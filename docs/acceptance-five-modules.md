# Synthesys-5: минимальный полноценный компьютер — приёмочный профиль

**Статус:** ОБЯЗАТЕЛЬНЫЕ ТРЕБОВАНИЯ К ПЕРВОЙ ПОЛНОЙ СИСТЕМЕ. Метрики — **проектные критерии приёмки**, не результаты проведённых тестов. Версия профиля: 2026-11-17.

## 1. Что такое «минимально работает»

Минимально работоспособная система — **одновременно установленные и взаимодействующие пять отдельных процессорных модулей ESP32-S3 N16R8: CPU, Storage, Video, Sound и Input**. Нельзя объявить весь компьютер готовым по результатам стенда CPU↔Storage или работающего VGA-паттерна. Промежуточные M0–M7 подтверждают только компоненты, полный PASS возможен **после системного 5-модульного испытания**.

Названия `Sound` = исторический `Audio`, `Input` = исторический `HID` (те же роли и команды; исходники могут продолжать использовать `audio_*`, `hid_*`). Отдельная физическая карта каждого из пяти модулей обязательна. CPU + четыре занятых периферийных слота; остальные слоты backplane резервируются для расширений.

| Модуль | Обязательные рабочие функции | Независимость |
|---|---|---|
| CPU | shell/boot, запуск демонстрации/игры, VFS FAT32, назначение ресурсов, команды и арбитраж HESS | логика игры исполняется локально |
| Storage | SDMMC, raw LBA reads/writes, direct block transfer с проверкой целостности | не требует CPU копировать блоки данных |
| Video | локальный renderer: текст, примитивы, тайлы, спрайты, палитра/буфер кадра, стабильный видеосигнал | scanout не останавливается на чужом grant |
| Sound | ≥4 независимых программных голосов, генератор/PCM, микширование, I2S → ЦАП | нет звукового потока отсчётов от CPU |
| Input | **один реально работающий интерфейс: PS/2 ИЛИ USB Host HID**, события клавиш; мышь желательно, но не обязательна для первого PASS | опрос и FIFO независимо от доступности HESS |

USB Host вместо PS/2 — допустимый вариант Input при выполнении **тех же проверок задержки и потерь событий**, не обязанность реализовать оба интерфейса. Для USB Host необходимо реальное VBUS-питание/защита и доступ к USB OTG; интерфейс USB нельзя без проверки одновременно использовать под native USB-JTAG. См. официальные примеры Espressif в разделе «Источники».

## 2. «Не ниже ZX Spectrum» — измеримые требования

ZX Spectrum — ориентир **пользовательского опыта для 2D-игр, управления и звука**, а не инструкция эмулировать Z80, ULA или дискретную звуковую систему. Пользователь запускает интерактивную игру/демо, видит плавную картинку, мгновенно реагирующие кнопки, слышит непрерывную музыку и эффекты.

| Показатель | Обязательный критерий для итогового PASS | Как мерить |
|---|---|---|
| Логическая графика | режим **не менее 256×192**, изображение с минимум 16 доступными цветами, текст, примитивы, скроллинг одной тайловой карты и **16 движущихся спрайтов** в стандартной сцене | воспроизводимая сцена, CRC/скриншоты, проверка всех примитивов |
| Вывод на экран | **стабильный видеовывод ≥50 Гц**; целевой экран VGA 640×480@60 (скалирование логического изображения допускается) | осциллограф/монитор, нет срывов синхронизации и видимых артефактов |
| Логика игры и обновление сцены | **≥50 обновлений/с в контрольной сцене**; p99 кадра ≤25 мс; пропущенные игровые кадры ≤0,1% в 30-минутном прогоне | таймер CPU, sequence frame, запись и счётчики Video |
| Звук | **≥4 одновременных голоса**; 16-bit 22,05 kHz mono mixed-output (или качественнее); во время прогона **0 I2S underrun** | счётчики Audio/I2S, запись осциллографом/аудиоинтерфейсом |
| Ввод | клавиатура PS/2 или USB, key down/up и повторы; **p95 задержки от аппаратного события до реакции игры ≤50 мс**, p99 ≤80 мс; **0 потерянных событий** в оговорённой нагрузке | GPIO/нажиматель + отметка реакции на экране, Input FIFO seq |
| HESS в штатной работе | **0 коллизий драйверов и незаконных владельцев**; **0 повреждённых блоков после CRC/retry**, 0 неразрешённых зависаний | hardware traces, тестовые счётчики, передача CRC данных |
| Прямая загрузка | Storage → Video и Storage → Sound, подтверждение resource READY, данные **не копируются через RAM CPU** | тестовые 64 KiB на каждого, контроль CRC/хэша в получателе |
| Загрузка ресурса | ориентир **≥100 KiB/s полезного payload** при прямой передаче и отсутствии конкуренции, на конфигурации всех пяти плат | измерять на полном стенде, не выводить из тактовой частоты |
| Длительная работа | **60 мин одновременно**: игра, музыка, ввод, фоновая прямая загрузка/повторное чтение; плюс **24 ч burn-in** с игровой нагрузкой по расписанию | 0 reset, 0 deadlock, 0 повреждений; логи питания, температура, CRC |

Второй уровень развития (НЕ условие первого PASS): 320×240, 8+ голосов и 44,1 кГц stereo, USB + PS/2 одновременно, сложные эффекты, динамическая загрузка больших карт мира. **Ни одна цифра выше пока не проверена на реальном железе**. При невозможности выполнить критерий документировать FAIL и менять реализацию или пересматривать цель отдельно, не переименовывать FAIL в успех.

## 3. Почему одна HESS может справиться с пятью модулями

Нет общей RAM; Video и Sound выполняют свои задачи самостоятельно. Но **CPU на время peer grant не может послать очередную команду Video/Audio или забрать событие Input**. Поэтому новая обязательная особенность первой версии — **ограниченные по времени гранты и обслуживание Input/CPU между порциями данных**.

### Правила арбитража — минимальная политика для пяти плат

- Только CPU/аппаратный арбитр выбирает один `OWNER` и один `TARGET`; схема OE обеспечивает реальный break-before-make и safe Hi-Z после reset.
- `ATTN_N` от Input, Sound, Video или Storage может быть активирован во время чужого grant и **не** требует захватывать общую шину. CPU обрабатывает его в следующем окне.
- В рабочем профиле ограничить непрерываемый peer grant проектным бюджетом **≤2 мс** (включая активный SPI обмен; фактическую задержку полного возврата владения измерить отдельно). Подобрать размер сегмента по частоте: **256 B @ 4 MHz ≈0,512 мс только по данным; 256 B @ 1 MHz ≈2,048 мс**, т.е. на низкой скорости нужны сегменты короче.
- После каждого гранта арбитр имеет возможность обслужить Input, короткие команды CPU, уведомления и задачи с более ранним deadline. Если очередь пуста — следующий грант bulk-передачи может стартовать сразу.
- Дедлайн короткой управляющей операции при полной пяти-модульной нагрузке: **p99 ≤5 мс от постановки в очередь до начала обслуживания**, кроме документированных boot/load экранов; обязательный замер, пока не гарантия.
- Ввод не теряется даже при дольше занятой шине: Input локально собирает FIFO **≥256 событий**, `seq`/overflow counter и `ATTN_N`. При overflow система обязана сообщить об ошибке; бесшумная потеря запрещена.
- Video и Sound должны автономно продолжать scanout/микширование; потоковые буферы и приоритеты локальных задач рассчитываются отдельно от HESS. На ESP32-S3 LCD RGB/EDMA и CPU конкурируют за PSRAM, что требуется проверить под нагрузкой.
- При истечении grant аппаратно закрыть master OE, отметить передачу aborted/uncertain и вернуться к CPU. Коллизия драйверов — критический отказ; нельзя «лечить» только программными retry.

**Двух миллисекунд недостаточно для гарантированного завершения любой транзакции** без handshake slave. Для P1 обязателен выбор таймаутов, согласование ready и экспериментальное измерение времени CS/rearm. При необходимости делить загрузку на меньшие куски, но нельзя удерживать общую шину на секунды и одновременно обещать низкую задержку Input.

## 4. Демонстрация, которая действительно доказывает пять модулей

**Synthesys-5 Demo** — единственный обязательный интеграционный пример для первого milestone FULL PASS:

1. CPU стартует с SD, читает конфигурацию, обнаруживает **все пять** плат, показывает их статусы.
2. Запускается контролируемая сцена 256×192: скроллинг карты, 16 движущихся спрайтов, UI текст, 50 логических обновлений в секунду.
3. Sound одновременно воспроизводит музыку и эффекты минимум на 4 голосах.
4. Input обеспечивает клавиатурное управление; отдельный генератор событий проверяет поток нажатий и отпусканий, последовательности и latency.
5. CPU периодически загружает из Storage новые ресурсы **напрямую** в Video и Sound небольшими грантами; уже играющие ресурсы продолжают работать.
6. Команды от CPU → Video/Sound и события Input должны обслуживаться между пакетами.
7. После 60 минут сравнить FPS histogram, audio underrun, input event seq, HESS arbiter/OE collision counters, CRC/load failures, reset reasons; затем провести 24-часовой burn-in.

Для первой версии не обязателен **динамический ELF-загрузчик**: демо может быть встроенной программой, но полнофункциональный boot/runtime из Storage и direct resource load обязательны; ELF — следующий программный этап.

## 5. Измерения, а не заявления

Публиковать данные для конкретной сборки: версии прошивок/ESP-IDF, длина витой пары и МГТФ, модуль N16R8, питание, topologies, SPI clock, сегмент, payload throughput, измерения SPI REQ/GRANT и реальные latency/FPS. Нельзя называть рабочим «без лагов» устройство, где нет записанных измерений и визуального теста.
