# Архитектура «Синтезиса»

## Модель: координируемая распределённая вычислительная система

Каждый модуль — автономный процессор ESP32-S3 с собственной RAM/PSRAM и локальными задачами. Центральный CPU исполняет программу и распределяет задания. Нет общей памяти: указатель в RAM CPU **никогда** не означает адрес памяти Video/Audio.

```text
              CPU (координатор, ОС, ELF, FAT32)
                         │
             адреса + гранты + HESS
   ┌─────────────────────┼─────────────────────────┐
 Storage                Video                    Audio         HID       ...
 SDMMC                  VRAM                     буферы        ввод
 raw LBA                renderer/scanout         mixer/I2S    события
   └─────────────── прямые передачи ──────────────┘
                  (по одному каналу HESS)
```

## Не путать четыре роли

- **CPU (координатор):** системный арбитр, файловая система, права/квоты на операцию, загрузка приложений, протокол управления.
- **Владелец HESS (bus master):** на время гранта выдаёт CLK и ведёт выбранную транзакцию. Может быть CPU или любой совместимый модуль.
- **Адресат (bus slave):** получает CS_N от дешифратора, отвечает на SPI-такты; не инициирует их.
- **Исполнитель задачи:** выполняет графику, аудио, ввод, кодирование, сетевые операции независимо от владения шиной.

## Короткие команды vs большие ресурсы

Управление: `DRAW_TEXT`, `DRAW_SPRITE`, `PLAY_SAMPLE`, `GET_STATUS` — короткие транзакции CPU → модуль.

Загрузка: CPU разрешает известный файл (экстенты секторов + длина логического содержимого), создаёт `transfer_id`, подготавливает стороны и отдаёт владельцу HESS грант на обмен с адресатом. Данные идут **не через RAM CPU**. Программе выдается будущий идентификатор ресурса; после `TRANSFER_COMPLETE` он становится доступен.

## Почему одна шина достаточна сейчас

- Видео **не** получает поток кадров: строит изображение в собственной памяти и формирует физический выход локально.
- Аудио **не** получает поток отсчётов в реальном времени: локально генерирует и воспроизводит звук.
- Storage нужен в основном для загрузки приложения, ассетов и эпизодических чтений/записей.
- В момент одной транзакции HESS занята одним master и одним slave, **остальные процессоры продолжают свою локальную работу**.
- CPU вправе синхронно ждать загрузку для простых программ. Асинхронные операции и буферизация нужны как расширение, не как условие первого запуска.

## Открытое расширение

Любой модуль может объявить capability `HESS_MASTER`/`HESS_SLAVE` и протокол задач. В будущем Network → Decoder, Camera → Storage, Compute → Video и пр. допускаются одной моделью без закрепления высокоскоростной шины за Storage. CPU должен согласовать любую пару модулей и план передачи.

## Ограничения

1. Один общий канал = максимум одна bus-транзакция одновременно.
2. Для peer-to-peer нужен не только протокол: **гарантированный Hi-Z** всех прочих передатчиков.
3. По SPI2/SPI3 доступность и совмещение ролей на ESP32-S3 зависят от прошивки и пинов и проверяются на M2/M3.
4. Нет гарантированной микросекундной задержки CPU во время гранта; на старте ожидание допускается.
5. Видеовывод и аудио должны переживать паузы HESS, пока есть готовые локальные ресурсы.

## Synthesys-5 — системные инварианты

Для первого полноценного компьютера обязательны **CPU, Storage, Video, Sound, Input** как пять отдельных процессорных плат. Не только каждой по отдельности: играть, выводить и смешивать звук, обрабатывать ввод и подгружать ресурс они должны **одновременно**. При нагрузке короткие управляющие сообщения CPU и Input обрабатываются между ограниченными во времени HESS peer grants. Входные события сохраняются в локальной очереди Input, видео и музыка продолжаются из локальной RAM даже при занятой HESS. Критерии и метрики — [Synthesys-5 acceptance](acceptance-five-modules.md).

Перегрузка HESS не должна автоматически означать потерю нажатия; если задержка перехода владения слишком велика, надо ограничить квант передачи, а не требовать отдельной шины без измерений.
