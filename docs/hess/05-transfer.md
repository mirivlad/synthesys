# Прямые передачи между произвольными модулями

## Общий API

```c
transfer_id = hess_prepare(
    source_device, destination_device,
    read_or_write, resource_capability, offset, length);
hess_wait(transfer_id, timeout_ms);  // v1 synchronous
// позже: hess_poll(transfer_id), hess_cancel(transfer_id)
```

Этот API описывает политику CPU. Непосредственный SPI master может быть **источником или получателем** полезных данных, потому что master определяет тактирование, а не направление полезного потока. Для Storage → Video на P2 Video может быть master, Storage slave.

## Полномочия и файл

- В файловом API передаются пути; на физическом HESS **передаются только заранее одобренные CPU экстенты LBA** и точная логическая длина ресурса.
- Storage не понимает FAT32 и не знает абсолютного назначения адреса в чужой PSRAM. Целевой модуль сам распределяет локальную память.
- CPU должен удерживать согласованность FAT32: блокировать конфликтующие записи/размонтирование пока открыт доступ к экстентам; заново перечитывать карту расположения файлов при изменениях.
- Для перезаписи Storage обязательны границы и подтверждение коммита; запрет записывать произвольные LBA без регистрации операции.
- Совместимы будущие Network → Compute, Camera → Storage, Coprocessor → Video при соответствующих capabilities.

## Порядок операций

`NEW → PREPARED_SRC → PREPARED_DST → GRANTED → ACTIVE → RELEASED → VERIFIED → COMPLETE`.

При любой ошибке: `ABORTING → RECOVERY → FAILED/UNCERTAIN`. Отчёт `COMPLETE` выдаётся только когда принимающая сторона подтвердила итоговый размер и целостность/доступность ресурса; один `BUS_IDLE` недостаточен.

## Потоковые сегменты

Преимущественно небольшие фреймы с `offset`, `len`, `CRC`. Для ESP32-S3 Slave DMA важна предварительная постановка буфера в очередь и handshake готовности. Не рассчитывать на гарантированный отклик slave в тот же момент, когда хост потянул CS. Если Buffer не готов, мастер **не** отправляет значимый кусок; сначала проверяет ready/status и ограничивает ожидание.

## Ожидание CPU

Для запуска приложения допустимо CPU `wait` на загрузку Video/Audio. На более позднем этапе CPU может исполнять независимые задачи и опрашивать `ATTN_N`. Ни то ни другое не требует второй полной шины.

## Ограничение

При GRANТ peer CPU не отправляет по HESS новые команды. Если в будущем потребуется низкая задержка независимо от больших передач, тогда отдельно изучить узкую out-of-band служебную линию или два сегмента шины, но **не делать это обязательным для текущего P1**.

## Ограниченные передачи и обслуживание ввода

Для пятимодульной системы **не выдавать grant на весь файл**. Передача Storage→Video или Storage→Sound разбивается на небольшие транзакции, между которыми CPU отбирает управление и проверяет: Input ATTN/FIFO, готовность Video/Sound, игровые команды, следующую готовность SPI Slave. Для обычной игры ориентир 256 B при 4 MHz; размер и бюджет должны быть уточнены измерениями, включая overhead, CS setup и DMA requeue.

Нельзя просто держать `OWNER=Video` несколько секунд и утверждать, что ввод не лагает. Допускается начальная блокирующая загрузка программы до старта игры, но в stress-test [Synthesys-5](../acceptance-five-modules.md) нужна и фоновая загрузка при активных пяти модулях.
