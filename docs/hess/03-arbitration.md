# Передача владения HESS: протокол и безопасность

## Состояния

```text
CPU_OWNED → PREPARE → QUIESCE → GRANT_PEER → PEER_ACTIVE → RELEASE → CPU_OWNED
                     ↘ TIMEOUT/FAULT → HARD_DISABLE → RECOVER → CPU_OWNED
```

### CPU_OWNED

Разрешён драйвер CPU, все другие master-драйверы в Hi-Z. Периферийные slave по умолчанию только принимают свои CS_N. CPU может отправлять команды и опрашивать статус.

### PREPARE

CPU создаёт `transfer_id`, определяет `owner`, `target`, направление, команду/диапазоны, максимум байтов и deadline. Проверяет `owner != target`, совместимость физического интерфейса, готовность DMA/буферов и разрешение к данным.

### QUIESCE

Дождаться завершения всех SPI транзакций CPU, деактивировать `XFER_N`, отключить master-драйвер CPU, подождать guard interval. Убедиться, что target slave подготовлен. Драйверы периферии пока закрыты аппаратно.

### GRANT_PEER

CPU переключает `OWNER`, `TARGET` при неактивном `XFER_N`. Backplane выдает `GRANT_N` только выбранному модулю, его master-буферы разрешаются. CPU **остаётся** владельцем управляющих выборов, но не может передавать данные по HESS, пока peer активен.

### PEER_ACTIVE

Peer управляет CLK/XFER и MOSI; выбранный slave отдаёт MISO. Максимальная продолжительность и размер транзакции указаны в grant. Peer обязан остановить CLK, поднять XFER и физически освободить свои выходы до завершения передачи. Можно передать длинный файл по нескольким кратким квантам.

### RELEASE

Peer сигнализирует окончание по `ATTN_N` **после** ухода в Hi-Z; CPU аппаратно отнимает grant, ждёт guard interval, включает свои драйверы, опрашивает обоих по `transfer_id` и завершает операцию. `ATTN_N` — OR-событие, не подтверждение успешной записи.

## Что происходит при сбое

| Сбой | Восстановление |
|---|---|
| Peer не начал передачу | CPU ждёт короткий deadline → отзыв grant → статус |
| Peer перестал отвечать | аппаратно закрыть его OE, снять CS, отметить ABORTED |
| Target удалён/неготов | остановить обмен, не читать старые буферы |
| Оба считают себя владельцами | аппаратная логика НЕ разрешает 2 master OE; ошибка фиксируется |
| CPU перезагрузился | supervisor безопасно отключает все OE; owner reset default |
| CRC / length mismatch | отклонить сегмент, retry лишь на той же незафиксированной операции |
| Неизвестна судьба записи | состояние UNCERTAIN; read-back/status по ID, не blind retry |

## Требование к железу

**Один лишь GPIO `GRANT_N` на входе ESP32 — недостаточная защита.** Внешние физические выходы должны быть за безопасными разрешаемыми буферами, управляемыми CPU/backplane logic. В модуле master CLK/MOSI/XFER не должны иметь прямого обходного пути к общему жгуту. Выход MISO slave открывается только адресным CS/transaction gate; reset заставляет его в Hi-Z. Конкретная схема буферов и default pull-up — отдельный этап M0 перед пайкой.

## Производительность

P0 стартует с 100 кГц и 128–512 байт на сегмент, затем 1–4 МГц; grant применяется на *задание или ограниченную серию сегментов*, а не на любой системный байт. Поддержка 8–10 МГц рассматривается только после сравнения ошибок и осциллограмм. Ограничение общей шины никогда не тормозит локальное выполнение модулей, если они не ждут нового ресурса.

## Политика для всех пяти модулей (обязательна для FULL PASS)

**Сам факт, что другой процессор выполняется локально, не означает отсутствия лагов:** CPU не обслужит команду или нажатие через HESS, если Video удерживает peer grant для длинной загрузки. Поэтому проектируется `bounded grant scheduler`:

1. Bulk-задания режутся на сегменты. Проектный предел непрерывного владения peer — ≤2 мс в рабочем режиме 4 MHz SPI (включая передачу; реальный переход между владельцами учитывается в тестах). 256 B занимают 0,512 мс на проводе при 4 MHz и 2,048 мс при 1 MHz **без служебных накладных расходов**.
2. Peer отпускает CLK/XFER/OE и подтверждает safe idle после короткого гранта. CPU аппаратно отзывает grant и получает возможность обрабатывать отдельные команды/события.
3. Если Input держит `ATTN_N`, CPU должен прочитать очередь Input прежде чем бесконечно продолжать bulk. Локальная очередь Input ≥256 событий с sequence и overflow-метриками.
4. События Video/Sound/Storage тоже учитываются; не допускать голодания ни одного устройства. Отладочный контроль: owner transitions, grant duration histogram, command wait histogram, missed deadlines.
5. Дедлайн короткой команды CPU (постановка → старт обслуживания) под пяти-модульной нагрузкой: **p99 ≤5 мс** как целевой критерий испытаний, не обещание уже готовой платы.
6. Приоритет электронно безопасного OE/timeout/abort выше любого scheduler policy; непредсказуемая готовность SPI slave и DMA должна блокировать старт соответствующей транзакции, но не зависать навсегда.

В boot/loading screen CPU вправе ждать окончания общей операции и иногда задерживать интерактивную сцену, но во время активной игры локальные Video/Sound/Input продолжать работу, а HESS регулярно возвращаться CPU. [Все критерии](../acceptance-five-modules.md).
