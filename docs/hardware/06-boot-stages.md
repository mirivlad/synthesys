> **Изменение P0:** с первого этапа CPU получает 5 В от backplane через HESS-40; терминал ПК по умолчанию подключается к **штатному USB Serial/JTAG**, с проверкой D1/D7/VBUS для конкретной DevKit. USB–UART 3,3 В — необязательный запасной способ. См. [power-first конфигурацию](09-backplane-powered-p0.md). Ранние шаги «запитать CPU от USB» больше неактуальны.

# Порядок разработки компьютера — от CPU-монитора до пяти модулей

## Базовая логика

**Согласованный итог — пять плат** CPU, Storage, Video, Sound, Input с независимыми вычислениями. Но не начинать с одновременной разработки всех пяти. Каждая новая плата добавляется к работающему предыдущему этапу.

| Этап | Состав | Умения компьютера | Подтверждение |
|---|---|---|---|
| **P0** | CPU | USB Serial/JTAG терминал с ПК; справка, состояние и ввод виртуальной клавиатуры; safe idle HESS | 1000 команд на UART/USB без зависаний, перенастройка USB |
| **P1** | CPU + Storage | HESS SPI, ping/status, SDMMC raw reads, FAT32 на CPU, `/boot.ini` | CPU читает boot config и распознаёт loader entry |
| **P2** | CPU + Storage | **загрузка исполняемой ОС из Storage** с сохранением ROM/flash rescue monitor; файловый коммандер в терминале ПК через USB-CDC (ANSI/VT100) | из SD запускается ОС, просмотр папок/файлов/копирование/удаление в безопасном режиме |
| **P3** | + Video | Video принимает команды CPU и локально выводит текст/окна/плитки; GUI коммандер на физическом видео, но пока ввод с ПК | экран работает независимо от USB-терминала |
| **P4** | + Input | PS/2 **или** USB Host keyboard, события с очередью, локальное управление GUI | отключение USB debug не лишает ОС ввода |
| **P5** | + Sound | микшер/I2S, ресурсы из Storage, игры, **все 5** модулей одновременно, стресс-тест Synthesys-5 | [FULL PASS](../acceptance-five-modules.md) |

**Этап P2 НЕ считается выполненным**, если ОС и файловый коммандер просто прошиты в CPU flash и не загружены с Storage. Плата CPU сохраняет маленький независимый monitor/bootstrap в своей flash. Загрузка ОС — после чтения Storage и проверки формата/ABI; поддержка ELF требует действительного загрузчика и динамических релокаций. Возможен промежуточный тест статически собранной ОС, но он не закрывает P2.

## Роль отладочного ПК

До Video + Input физический монитор и клавиатура не нужны: CPU через USB Serial/JTAG является `tty` устройства — выводит ANSI escape интерфейс, принимает клавиши от ПК, использует виртуальную очередь событий. После P3/P4 тот же USB остаётся инженерным интерфейсом с логами, профилированием и ручными командами.

Два отдельных потока USB можно добавить позже, но **P0 — один USB CDC канал** с текстовыми ответами и симуляцией ввода. Не путать с функцией USB HID Device на ПК.

## Разделение терминала и ОС

- Flash monitor / recovery: низкоуровневая диагностика, init HESS, поиск Storage, чтение boot.ini, ошибки boot.
- Bootloader OS: доверенная прошивка ESP32-S3 CPU ищет и загружает исполняемый образ с SD (Storage raw sectors).
- OS: tasks, VFS, файловый коммандер и shell; работает на CPU и знает HESS device APIs.
- Video/Input/Sound: собственные firmware, **не загружаются каждый раз с CPU**; CPU обнаруживает их протокол/версию.

## Непременные требования на всех этапах

1. Новые функции не должны убирать доступ по USB: failed boot возвращает в recovery monitor.
2. Ресурсам Video/Sound в будущей ОС разрешён **прямой** transfer Storage↔peer без копирования через CPU.
3. Ввод ПК работает в P2, когда Input отсутствует: это отладочная эмуляция клавиатуры, не штатный Input.
4. Никаких hot-swap, токовых конфликтов USB VBUS с HESS +5 V, конфликтов GPIO strap/Octal PSRAM.
5. Документировать проведённые тесты, а не считать перечень функций реализованным.
