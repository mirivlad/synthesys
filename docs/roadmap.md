# План разработки: P0–P5 и финальный Synthesys-5

**Обязательный итог** — CPU + Storage + Video + Sound + Input работают одновременно и выполняют [пяти-модульные испытания](acceptance-five-modules.md). **Порядок интеграции утверждён:** сначала CPU → Storage → загрузка OS + файловый коммандер → Video → Input → Sound (последним).

| Этап | Подключённые модули | Проверяемый результат |
|---|---|---|
| **P0 / M0** | CPU | USB Serial/JTAG монитор, безопасный HESS disabled, локальная диагностика, виртуальная клавиатура ПК |
| **P1 / M1–M4** | CPU + Storage | HESS ping, адрес/владение, SDMMC read/write, FAT32 CPU, `boot.ini`, CRC прямой передачи на тестовом peer |
| **P2 / OS** | CPU + Storage | **ОС действительно загружается с Storage**, ANSI/VT100 файловый коммандер и shell работают в USB-терминале ПК |
| **P3 / Video** | + Video | автономный text/tiles/sprite renderer, видеовыход, доступ CPU к Video API, получение ресурсов из Storage |
| **P4 / Input** | + Input | реальная клавиатура PS/2 **или** USB Host, Input FIFO, возможность работы ОС без клавиатуры ПК |
| **P5 / Sound** | + Sound | автономный I2S mixer, ≥4 голоса, прямая загрузка сэмплов, полноценный Synthesys-5 demo |

## P0 — подготовить железо

1. Подтвердить точный ESP32-S3 N16R8 DevKit, его USB и питание, найти реальные GPIO на гребёнках.
2. Принять [HESS-40 разъём](hardware/04-hess-40pin-connector.md), прозвонить питание/землю.
3. Проверить электрически hardware OE/OWNER/TARGET/break-before-make, **не подключать общую SPI без драйверного interlock**.
4. Запустить [CPU recovery monitor](../firmware/cpu-monitor/README.md), убедиться в USB обмене с ПК.
5. Снять осциллограммы reset/Hi-Z/питания и только потом разрешать вывод HESS в P1.

## P1 — Storage и владение шиной

Сначала обычный SPI 1-bit CPU master ↔ Storage slave, M1: 10 000 ping без ошибок, затем проверка SDMMC (M2), FAT32 и `boot.ini` (M3). Для прямой передачи требуется арбитраж M4 на временном *test peer* (третья devkit не является полнофункциональным Video): CPU уступает HESS, test peer ← Storage, все OE проверены. Не объявлять P1 полностью готовым без CRC и возврата bus после timeout.

## P2 — загрузка ОС с SD

CPU flash содержит только recovery monitor/bootstrap. После проверки `boot.ini` loader читает исполняемый OS image с Storage, размещает в собственной RAM/PSRAM и запускает. **OS shell и файловый коммандер должны быть частью загрузившегося образа**, иначе это только демонстрационная прошивка. До появления Video и Input интерфейс является ANSI/VT100 приложением в терминале ПК (USB CDC). При неуспехе загрузки CPU возвращается в recovery monitor. ELF ABI/loader — отдельная техническая задача; статическая встроенная ОС не закрывает этот этап.

## P3 — Video

Video отдельно проходит standalone тесты видеосигнала/памяти, затем получает команды CPU и ресурсы прямым Storage→Video. CPU GUI файловый коммандер рисует через команды Video (не поток кадра). Интерактивность пока обеспечивается PC USB terminal.

## P4 — Input

Input обслуживает PS/2 либо USB Host клавиатуру, FIFO и ATTN_N; CPU теперь управляется от реальной клавиатуры. Отладочная USB консоль остаётся независимо доступной.

## P5 — Sound и системная приёмка

Sound отдельно проверяет I2S, микшер и буфер, затем работает с Video, Input, Storage и CPU в общей системе: 50 игровых обновлений/с, минимум 16 спрайтов, 4 независимых голоса и приём событий клавиатуры, включая фоновые передачи ресурсов. **Ни один предыдущий P0–P4 не является полноценным пяти-модульным ПК.** Выполнить [60 минут + 24 часа burn-in](acceptance-five-modules.md), с осциллограммами, latency/FPS/audio/drop статистикой.

## Следующие расширения после P5

Полноценный загрузчик ELF и ABI (если в P2 был иной исполняемый формат), улучшения VGA/цвета, графические и аудио API, SDK для сторонних модулей, тесты 8 слотов. QPI после подтверждения ESP-IDF PHY на реальной пяти-модульной HESS, а не вместо программной оптимизации.
