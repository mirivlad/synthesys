# CPU и Storage

## CPU — системный координатор

Отвечает за reset/POST, обнаружение слотов, API устройств, исполняемые программы, FAT32, `boot.ini`, загрузчик ELF, обработку ошибок и арбитраж HESS. CPU **не** составляет видеокадры и не синтезирует PCM для обычной работы. Обращается к периферии высокоуровневыми командами.

При неисправном Storage/Video сохраняется rescue monitor по USB/UART: `hess scan`, `status`, `ping`, `mem`, `trace`, `reset slot`.

При открытии файла CPU хранит метаданные FAT32, формирует физические экстенты (не пути!) для разрешённой прямой передачи. На время операции запрещает конфликтующее изменение файлов/секторов. Программа получает handle ресурса и завершение операции, но не произвольный физический LBA.

CPU удерживает права владельца посредством `OWNER`/`TARGET`/gates и организует передачу между **любой совместимой парой**, в том числе без Storage. CPU может блокирующе ждать завершения на первом этапе.

## Storage — отдельный блочный компьютер

На своей ESP32-S3 обслуживает SD-карту по SDMMC (вначале 1-bit, потом 4-bit), карту как блочное устройство, read/write LBA, card detect, IO errors. **Файловую систему не монтирует** в штатном варианте, не знает имён файлов, не запускает приложения.

При direct transfer:
1. CPU подготавливает Storage с transfer_id и разрешёнными экстентами.
2. Storage готовит буферы/очереди SPI Slave.
3. Например, Video получает grant как SPI Master и тактирует чтение из Storage, не копируя содержимое в RAM CPU.
4. Storage сообщает статус, объём, CRC, ошибки. После снятия гранта CPU сверяет результаты обеих сторон.

Запись в Storage требует идемпотентности и read-back при неопределённом состоянии. При исчезновении карты завершить ожидающие задания с ошибкой, не повреждать произвольные сектора.

## Базовые команды

`STORAGE_GET_GEOMETRY`, `STORAGE_READ_BLOCKS`, `STORAGE_WRITE_BLOCKS`, `STORAGE_PREPARE_EXTENTS`, `STORAGE_TRANSFER_STATUS`; детали в [протоколе](../hess/04-protocol.md).

## Буферы

При DMA учитывать выравнивание и реальные требования ESP-IDF, очереди slave и пропускную способность PSRAM; большие transfer_id сегментируются. Потоковый режим не обязывает Video/Audio быть SPI master; master выбирается по заявленным возможностям и направлению обмена.

## Уточнённая последовательность включения CPU/Storage

**CPU P0:** встроенный USB Serial/JTAG recovery monitor в CPU flash, клавиатурные команды с ПК. **P1:** HESS↔Storage, SDMMC + FAT32 на CPU, поиск loader. **P2:** загрузка исполняемого образа ОС с Storage (внутри ОС — файловый коммандер, работающий через ANSI/VT100 на USB-терминале ПК). Только затем Video, Input и Sound. Отсутствие любого другого модуля не лишает CPU восстановления по USB. [Подробно P0–P5](../hardware/06-boot-stages.md).
